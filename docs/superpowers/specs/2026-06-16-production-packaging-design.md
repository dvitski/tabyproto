# Production Packaging & Auto-Update Design

**Date:** 2026-06-16
**Status:** Approved

## Summary

Package the Taby desktop app as a Windows `.exe` installer with silent delta auto-updates served from a private server. Updates are applied at launch before the UI appears; a failed update never prevents the app from starting.

## Constraints

- Windows only (SMTC/USB HID dependencies)
- Private server for distribution
- No Windows code signing certificate
- Silent install (no user prompt for updates)
- Delta/patch updates (not full download each time)

## Approach

**Update4j + jpackage.** jpackage (built into the Compose Desktop Gradle plugin) produces a self-contained `.exe` installer with a bundled JRE. Update4j acts as a bootstrap launcher: on each startup it fetches a manifest XML from the server, downloads only JARs whose checksum has changed, then launches the real app.

The ~70 MP4 animation files are extracted into a dedicated `anim-resources` Gradle module so they form a separate JAR with its own checksum. This means code-only releases download only `api.jar` + `desktop.jar` (a few MB), while animation updates download `anim-resources.jar` (~100MB) only when animations actually change.

## Architecture

### Installed layout

```
%AppData%\Local\Taby\
  Taby.exe                  ← native launcher (jpackage)
  runtime\                  ← bundled JRE (jpackage)
  app\
    bootstrap.jar           ← Update4j launcher (baked into installer, never auto-updated)
    api.jar                 ← core library
    desktop.jar             ← UI code
    anim-resources.jar      ← all MP4 animations (~100MB)
    update4j.jar            ← Update4j library
```

### Gradle modules

```
tabyproto/
  api/                      ← unchanged
  anim-resources/           ← NEW: contains anim/*.mp4, no code
    build.gradle.kts
    src/main/resources/anim/   ← MP4s moved here from desktop/
  bootstrap/                ← NEW: Update4j launcher; depends only on update4j
    build.gradle.kts
    src/main/kotlin/Launcher.kt
  desktop/                  ← depends on :api, :anim-resources, and :bootstrap (runtimeOnly)
    src/main/resources/anim/   ← emptied (files moved to anim-resources)
```

`desktop` adds `runtimeOnly(project(":bootstrap"))` so jpackage picks up `bootstrap.jar` when bundling. `bootstrap` does not depend on `desktop` — it only knows `desktop`'s main class name as a string passed to Update4j's launcher.

## Components

### `anim-resources` module

No code. One job: bundle all MP4s into a JAR so they have an independent checksum.

`AnimationResources.kt` already loads files by name via `getResourceAsStream("/anim/$id.mp4")` — no code changes required. The classpath lookup finds the files in `anim-resources.jar` automatically.

### `bootstrap` module

```kotlin
// bootstrap/src/main/kotlin/Launcher.kt
fun main() {
    val config = runCatching {
        Configuration.read(
            URI("https://yourserver/taby/update.xml").toURL()
                .openStream(/* 500ms connect timeout */).reader()
        )
    }.getOrNull()

    config?.runCatching { update() }  // download changed JARs; errors are swallowed
    config?.launch()                  // hand off to desktop MainKt
        ?: launchExisting()           // fallback: launch with current classpath
}
```

Update4j verifies checksums after each download and aborts the update (leaving old JARs intact) if any mismatch is detected.

### Server manifest (`update.xml`)

Generated by Update4j's CLI tool from the assembled JAR folder. Regenerated on every release.

```xml
<configuration timestamp="2026-06-16T12:00:00">
  <base-uri>https://yourserver/taby/</base-uri>
  <files>
    <file path="app/api.jar"            size="..." checksum="..." classpath="true"/>
    <file path="app/desktop.jar"        size="..." checksum="..." classpath="true"
          launcher="cc.dvitski.tabyproto.desktop.MainKt"/>
    <file path="app/anim-resources.jar" size="..." checksum="..." classpath="true"/>
  </files>
</configuration>
```

`bootstrap.jar` and `update4j.jar` are intentionally absent from the manifest — they are bundled in the installer and treated as stable. Only `api.jar`, `desktop.jar`, and `anim-resources.jar` are managed by Update4j.

The installer bundles all JARs for first-run so there is no large initial download after install.

### jpackage configuration (`desktop/build.gradle.kts`)

```kotlin
compose.desktop {
    application {
        mainClass = "cc.dvitski.tabyproto.bootstrap.LauncherKt"
        nativeDistributions {
            targetFormats(TargetFormat.Exe)
            packageName = "Taby"
            packageVersion = "1.0.0"
            windows {
                iconFile.set(project.file("src/main/resources/icons/icon.ico"))
                menuGroup = "Taby"
                upgradeUuid = "<generate-once-never-change>"
                perUserInstall = true  // installs to AppData; no admin needed for JAR updates
            }
        }
    }
}
```

`perUserInstall = true` is critical: it installs to `%AppData%\Local\Taby`, which is user-writable, so Update4j can replace JARs without elevation.

`TargetFormat.Exe` produces an NSIS installer. No code signing certificate required; users see a Windows SmartScreen "unknown publisher" warning on first install only.

`upgradeUuid`: generate once with any UUID generator and commit it. NSIS uses it to detect and uninstall previous versions automatically.

## Update Flow

```
User launches Taby.exe
  └─ bootstrap.jar starts
       ├─ fetch update.xml from server (500ms timeout)
       │    ├─ success → compare checksums
       │    │    ├─ all match → skip download
       │    │    └─ mismatch → download changed JARs to temp, move into app\
       │    └─ failure → skip update entirely
       └─ launch desktop MainKt with current app\ classpath
```

Updates apply before the UI appears. No restart required — the freshly-downloaded JARs are used on that same launch.

## Error Handling

| Failure | Behavior |
|---|---|
| Server unreachable / timeout | Skip update, launch existing version |
| Download interrupted | Leave old JAR in place, launch existing version |
| Checksum mismatch after download | Update4j discards corrupt file, launches existing version |
| `update.xml` malformed | Catch exception, log to `%AppData%\Local\Taby\update.log`, launch existing |

A failed update is never fatal. The app always launches.

## Release Workflow

1. `./gradlew assemble` — produces all JARs under `build/`
2. Run Update4j manifest generator against the assembled JARs → `update.xml`
3. Upload changed JARs + `update.xml` to private server
4. Users get the update on next launch automatically

New installer (`.exe`) is only needed when `bootstrap.jar` itself changes, which should be rare.

## Version Display

A `version.properties` file (written by a Gradle task at build time, bundled in `bootstrap.jar`) exposes the current version string to the Settings screen. The manifest `timestamp` attribute serves as the release identifier in logs.

## Out of Scope

- macOS / Linux packaging
- Code signing (revisit if SmartScreen friction becomes an issue for end users)
- Rollback (failed updates leave old JARs; no explicit rollback mechanism)
